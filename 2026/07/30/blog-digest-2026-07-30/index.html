1. How GPT-5.6 fuses frontier intelligence with frontier efficiency

来源：OpenAI Engineering
作者：OpenAI 技术团队
日期：2026-07-29

核心概要

OpenAI 这篇工程博客详细拆解了 GPT-5.6 模型家族在效率层面的技术实现。文章聚焦两个超出模型本身的关键优化领域：推理栈（inference） 和 Agent 编排层（agentic harness）。

推理优化方面，文章覆盖了负载均衡、投机解码（speculative decoding）、KV 缓存管理和内核优化。特别值得注意的是，GPT-5.6 Sol 自身在 Codex 中”反哺”了这些优化——它分析了生产流量、重写了 Triton/Gluon 内核、设计并运行了投机解码器的实验、甚至监控了训练过程并在硬件故障时自主介入。这些努力将端到端服务成本降低了 20%，投机解码效率提升了 15% 以上。

Agent harness 部分同样值得细读。OpenAI 的 harness 是一个 Rust 编排层，连接模型、工具和用户环境。两个关键设计是：延迟发现（deferred discovery）——让插件和 MCP 工具只在需要时才暴露到上下文中，避免上下文膨胀；以及 append-only 历史设计——所有模型可见的历史只追加不插入，最大化 prompt cache 命中率。工具输出默认上限 10000 tokens，防止单个工具意外吞噬上下文窗口。

关键洞察

  • GPT-5.6 Sol 自主优化了自身推理栈：它重写了生产内核、设计了投机解码器实验、超参优化了 KV 缓存配置。这展示了一个”模型优化自身基础设施”的闭环范式。
  • 内核优化用了 Triton 和 Gluon 两种 GPU 编程语言，配合开源工具 FpSan（浮点数消毒器）验证正确性。这说明 AI 写 GPU 内核已经有了完整的工具链。
  • Prompt caching 的最佳实践是 append-only + 确定性排序：新消息只追加到尾部、工具定义按确定性顺序排列、运行时设置延迟到执行阶段。这个设计直接贡献了 Codex 和 ChatGPT Work 的高缓存命中率。
  • 效率优化是复利过程：单看每一项改进都有限，但负载均衡、内核、投机解码、缓存这些优化层层叠加，才能同时做到前沿智能和前沿效率。

评价

优点：这是难得一见的”推理工程 + Agent harness”双线深度技术文章。Rust harness 的架构设计（deferred discovery、append-only context）对任何构建 Agent 系统的人都有参考价值。GPT-5.6 Sol 自主优化内核和训练流程的案例，是”AI for AI infra”最具体的公开案例之一。

不足：文章带有明显的 OpenAI 产品宣传色彩，GPT-5.6 的具体能力指标（如”超越 Claude Fable 5”）缺乏可验证的第三方数据。部分技术细节（如负载均衡路由策略）停留在概念层面，没有给出可复现的工程参数。

适用场景：AI 基础设施工程师、Agent 系统架构师、对推理优化感兴趣的研究者。

推荐指数

⭐⭐⭐⭐ (4/5) — 推荐阅读。技术深度足够，harness 设计理念值得借鉴，但需过滤掉产品宣传部分。

2. 做完一次总体设计后，我重新理解了企业级知识库

来源：卢向东的博客
作者：卢向东
日期：2026-07-29

核心概要

这篇文章是作者在企业级智能知识库项目完成总体设计后的系统性复盘。文章的核心论点是：企业级知识库的真正门槛不是能上传多少种文件，也不是某次测试的准确率，而是能否建立一套让知识持续进入、持续使用、持续发现问题并持续优化的运行机制。

文章提出了一个完整的”知识供应链”框架，将企业知识库工作划分为四个阶段：构建知识 → 治理知识 → 使用知识 → 优化知识。这个闭环不是架构图上画一条返回箭头那么简单，而是要回答一系列具体的运营问题：反馈由谁接收？问题如何分类？哪些可以自动处理？哪些需要业务人员判断？

特别有价值的是文章提出的双层知识组织方式：知识库按组织管理归属建设（解决”谁拥有、谁维护、谁授权”的责任问题），知识空间按业务主题跨库汇聚（解决”完成一项工作需要哪些可信知识”的场景问题）。这直击了企业中知识管理责任纵向化与业务场景横向化之间的根本矛盾。

此外，文章还深入讨论了知识生命周期管理（接入、加工、审核、发布、使用、更新、失效、归档）、知识加工作为低代码编排过程、可信问答的证据溯源链路，以及知识健康度监控等关键设计。

关键洞察

  • “知识库”与”知识空间”的分离是核心架构洞察：管理责任是纵向的（风控部管风控制度、运营部管流程），但业务场景是横向的（一个贷款审批助手需要同时调用风控、运营、科技规范）。复制知识会破坏权限和来源，授权汇聚才是正解。
  • 知识生命周期管理是企业级与玩具级 RAG 的分水岭：普通工具关心”现在能不能问到”，企业系统还必须关心”这条知识现在是否应该被问到”。草稿不应被检索到，旧版本要有过渡期规则。
  • 可信问答的关键是白盒可溯源：答案不只是显示引用编号，而是能回到原始文件的具体页码、章节、高亮片段，并保留当时使用的文档版本。这让运营人员能精确定位问题出在召回、排序还是知识本身。
  • 知识加工不是一次性 ETL，而是持续运转的基础设施：知识更新后重新触发加工、健康检查发现低质量切片后重新解析、用户反馈沿引用链修复——这些闭环机制才是企业知识库的生命线。
  • 企业知识建设不能假设所有事情都能在一次自动流程中完成：人工审批节点需要保存流程状态、释放计算资源、审批完成后继续执行。这种细节设计直接影响系统的可用性。

评价

优点：这是我近期读到的关于企业级知识库设计最系统、最务实的文章。作者从真实交付项目中提炼，不是纸上谈兵。知识库 vs 知识空间的双层架构、知识生命周期状态机、可信问答溯源链路等设计，都有很强的可落地性。文章结构清晰，从理念到架构到细节层层递进，配图也很好地辅助了理解。

不足：文章基于特定产品（TorchV AIS）的设计经验，部分方案可能带有该产品的特定假设。对于非企业级场景（如个人知识管理、小型团队），这套架构可能过于重量级。文章对 Agent 如何在知识空间中跨库工作只做了概念性讨论，缺乏具体的技术实现细节。

适用场景：企业 AI 系统架构师、知识管理平台产品经理、正在规划或构建 RAG/知识库系统的技术决策者。对于任何需要让 AI 在企业环境中”可信地”使用内部知识的人来说，这篇文章都值得反复研读。

推荐指数

⭐⭐⭐⭐⭐ (5/5) — 必读。这篇文章为企业级知识库设计提供了罕见的系统性和深度，从实践中来，有理念也有细节，是目前中文社区在这个话题上最好的文章之一。

3. 关于 Agent 的几个判断

来源：宝玉的博客
作者：宝玉
日期：2026-07-28

核心概要

这篇文章是作者对 Twitter 用户 @cellier_ 关于 Agent 三个判断的回应与延伸。原文判断是：”通用 Agent 会吃掉垂直 Agent”、”更开放的会吃掉更封闭的”、”更下沉的会吃掉更傲慢的”。作者在此基础上提出了自己的六个判断。

作者认为，不仅通用 Agent 会吃掉垂直 Agent，通用 Agent 赛道本身也会是少数赢家通吃。真正的开放与封闭之分不在于是否开源或能否切换模型，而在于插件生态——Claude Code 和 Codex 默认用自家模型并无大碍，关键是 Skill + MCP 构成的丰富生态。作者还指出，当前阶段的 Agent 产品本质上是在教育用户（如同曾经的”小龙虾”），产品忠诚度很低，模型能力和成本才是最终的护城河。

对于个人开发者和中小团队，作者的建议很直接：不要拼通用 Agent 或垂直 Agent，但基于 Agent 做插件（尤其以 Skill 为入口接入差异化服务）仍有窗口期。对普通用户则建议”越早用、越多用、多花一点钱用更聪明的模型”，并强调工程管理能力会越来越重要。

关键洞察

  • 模型是护城河，产品体验会趋同：Skills 和 MCP 绝大部分不具备独占性，用户最大的体验差异来自模型本身的智能程度。用过聪明的模型，就不会想回去。
  • 插件生态比模型可切换性更重要：Claude Code 和 Codex 都支持其他模型，但用户并不在意，因为生态本身才是粘性来源。
  • 前期 Agent 在教育用户，忠诚度极低：Claude Code 火过，Codex GUI 版很快抢走用户，WorkBuddy 又在服务用不了前两者的群体。这是增量市场，不是存量博弈。
  • Skill 入口 + 后端服务是中小团队的机会：单纯做 Skill 没门槛（已泛滥），但以 Skill 为入口接入差异化服务仍有窗口。

评价

优点：观点清晰、判断果断，没有模棱两可的套话。”模型是护城河”和”插件生态比模型可切换性重要”这两个判断有很强的现实解释力。对中小团队和普通用户的建议也比较务实。

不足：作为对一条推文的回应，内容深度有限，更多是观点陈述而非论证支撑。部分判断（如”少数通用 Agent 通吃”）缺乏论据，更像直觉判断。”信则灵”式的表述（关于 Agent 能否提升效率）削弱了说服力。整体篇幅较短，适合速读但不适合作为深度参考。

适用场景：关注 AI Agent 行业趋势的从业者、考虑做 Agent 相关产品的开发者、想了解行业玩家格局的观察者。

推荐指数

⭐⭐⭐ (3/5) — 值得参考。观点有启发性但论证深度有限，适合快速浏览获取行业判断，不适合作为决策的唯一依据。
