1. 从 TL 到 EM：我终于不再盯着 AI 写代码了

来源：baoyu.io
作者：宝玉
发布日期：2026-07-29

核心概要

这篇文章记录了作者在使用 Coding Agent 过程中一个真实而重要的角色转变：从 TL（Tech Lead） 模式切换到 EM（Engineering Manager） 模式。

在 TL 模式下，作者虽然不是事必躬亲，但系统设计、代码审查等环节都亲力亲为——本质上还是”对 AI 写的代码不放心”。这种做法虽然质量更有保障，但人本身成了 Agent 的瓶颈，大量决策和细节都压在一个人身上。

转折点出现在 Fable 5 前后，作者发现 AI 写的代码质量已经”相当可以了”，只要稍加验证就不会有太大偏离。于是他开始减少对 AI 写代码过程的干预，转而站在全局视角：决定项目怎么做，去验收好结果。具体流程是：先和 Agent 一起做技术方案 → 确认方案没问题 → 用 /goal 交给 Agent 执行（写代码 + 自动化测试）→ 做好后验收功能，代码不再细看。遇到 Bug，就把 Bug 描述给 Agent，让它自己重现、修复并补上测试覆盖。

作者还指出，这种 EM 视角带来了一个额外红利：技术选型不再被自己的技能树绑架。他开发字幕翻译 App 时，最初因为熟悉前端而选了 Electron，后发现性能不满意便果断换成 Swift + AppKit 原生栈（此前并不熟 Swift）；现在为 BaoCut 跨平台版本选型时首选 Rust——哪怕从未写过一行 Rust，借助 AI 也能毫无压力地完成第一个版本。

关键洞察

  • 角色定义决定协作效率：TL 与 EM 的核心差别在于”技术参与深度”。当人始终在代码层把关时，人就是流水线的瓶颈；切换到”定方向 + 验收结果”后，Agent 的生产力才被真正释放。
  • 信任是有临界点的：作者明确把 Fable 5 作为分水岭。这说明模型能力的提升会越过某个主观阈值，之后”盯过程”的成本收益就反转了。
  • 技术选型被个人技能束缚是一个隐性成本：很多团队的技术栈其实是”团队最熟什么就用什么”，而非”什么最适合”。AI 辅助让”用最合适的技术”变得可行，Electron → Swift → Rust 的迁移路径就是实证。
  • 瓶颈上移到”想清楚”：当写代码不再是瓶颈，真正的瓶颈变成了”想清楚该做什么”。作者在 BaoCut 每天一个小版本迭代，但构思大版本时速度立刻慢下来——因为人的思考没有跟上。

评价

优点：

  • 极其坦诚的个人经验，没有泛泛而谈，每一条结论都配有自己的真实项目（字幕翻译 App、BaoCut）作支撑。
  • “TL → EM”这个比喻非常贴切地刻画了当下 AI 编程协作中一个普遍却少被命名的转变，读完会让人重新审视自己和 Agent 的协作方式。
  • 流程描述具体可操作（技术方案 → /goal → 自动化测试 → 验收），对正在摸索 Agent 协作的读者有直接参考价值。

不足：

  • 篇幅较短，属于”观点 + 案例”的随笔，缺乏对不同项目复杂度、团队规模下该模式的边界讨论（例如：多人协作、遗留系统重构时 EM 模式是否同样成立？）。
  • “不再细看代码”对单人独立项目可行，但对需要代码可维护性、安全审计的团队场景需要更多补充，否则容易被误读为”完全放手”。

适用场景：独立开发者、小团队 Tech Lead、正在从”亲手写代码”过渡到”驱动 Agent 写代码”的工程师。如果你正在纠结”该不该信任 Agent 写的代码”，这篇会给你一个来自实践者的明确信号。

推荐指数

⭐⭐⭐⭐ (4/5) — 推荐。

理由：它精准命名了一个当下 AI 编程协作中真实发生、却少有人点破的角色转变（TL → EM），并用可复现的个人项目案例佐证，观点鲜明、可操作性强。扣一星是因为篇幅偏短、对团队/复杂项目场景的边界讨论不足，更像一篇高质量的随想而非系统方法论。
