把 Go 应用直接编译成鸿蒙原生 App（HAP）：调研记录

Nov 01 2026 技术

这篇是 2026-11-01 当天一轮调研的记录：能不能把 Go 写的桌面应用，直接编译成可以安装在鸿蒙 PC 上的原生 App（HAP）。结论先放在前面：路径在纸面和部分模拟环境里走得通，但真机（鸿蒙 PC）端到端还没有验证，下面所有结论都按这个前提来读。

文中的证据标记沿用调研时的约定：

  • [实跑]：在自己的电脑上亲手编译、运行验证过（不是鸿蒙真机）。
  • [源码] / [官方]：读源码或官方文档确认。
  • [摘要] / 推断：来自搜索摘要或推断，可信度最低。

需求背景

我现在用的是华为 MateBook Fold（鸿蒙 PC，HarmonyOS 6.x），想把好用的开发 / AI 工具搬到鸿蒙上来。

最先评估的是 egoist 的 MyGo，一个纯 Go 的 GUI 框架，风格类似 GPUI + Tauri。评估结论是不适合直接用：

  • 它的 Linux 后端依赖 GTK3 / WebKitGTK、X11 / Wayland、OpenGL，这些在鸿蒙上都没有；
  • 如果硬要用，只能编成 wasm 放在浏览器里跑；
  • 想做成原生，就得给它写一套新的平台后端，工作量是”月级”。

评估过程中有一个关键认识：鸿蒙 NEXT 的内核是自研的鸿蒙内核（兼容 Linux syscall ABI），C 库是 musl，并不是普通的 Linux arm64；而 Go 官方目前还没有 GOOS=openharmony，只能依赖社区 fork。

所以思路转向了更”薄”的架构：go-thin-app（参考实现是 yetone/magpie）。它的结构是：

  • Go 写领域逻辑；
  • net/http 提供 JSON API；
  • embed 打进去的纯 HTML / CSS / JS 做界面；
  • 桌面端只用 Wails 开一个窗口。

这样平台相关的部分就只剩”窗口外壳”一层，其余代码天然可以复用。

最终目标很明确：直接编译成可安装的鸿蒙原生 App（HAP），而不是在终端或虚拟机里跑。

方案

整体思路是：ArkTS 外壳 + ArkWeb（Web 组件）加载同一套 HTML；Go 后端编成 .so（cgo + 鸿蒙 NDK，-buildmode=c-shared），通过 NAPI 加载，在 App 进程内监听 127.0.0.1 起 HTTP 服务。HTML 与 API 和 Wails 版完全共用。

调研结果

1. Go 工具链

  • [实跑] star4277/ohos-go 的 tag v1.26.5-beta1（基于 OpenHarmony-SIG 的 ohos_golang_go，合并了 go1.26.5）可以编出工具链，go tool dist list 里包含 openharmony/arm64 和 openharmony/amd64。作为对比，SIG 官方分支只到 go1.24.5。
  • [实跑] 鸿蒙 NDK 可以公开下载，无需登录：ohos-sdk-windows_linux-public_20260829.tar.gz，约 3.7GB，内含 native-linux-x64-26.0.0.38，自带 OHOS clang 15.0.4。
  • [实跑] 用一个最小 demo（embed HTML + net/http 监听 127.0.0.1:0 + 导出一个 C 函数）验证了构建命令：

c-shared（约 8.8MB）和 c-archive 都能编出来。用 readelf 检查：NEEDED 是 libc.so（musl），有 PT_TLS，TLS 重定位只有 R_AARCH64_TLSDESC，没有 initial-exec（TPREL）。

  • [实跑] 对照实验：官方 Go 1.27.3 编 linux/arm64 的 c-shared，产物里是 R_AARCH64_TLS_TPREL64（initial-exec），musl 的 dlopen 会报 “initial-exec TLS resolves to dynamic definition”。上游的修复 PR 目前仍未合入。
  • [实跑] 在 Alpine musl 1.2.6 上做 dlopen（arm64 用 qemu-user）：fork 编出来的 .so 加载成功，外来 pthread 调用正常，curl 127.0.0.1 能拿到 JSON 和 HTML。局限要说清楚：这不是鸿蒙自己的 musl，不是真机，也没有经过 NAPI / ArkTS。
  • [源码] star4277 源码里，internal/platform/supported.go 允许 openharmony 使用 c-shared / c-archive / pie；runtime/tls_arm64.h 有 TLS_GD；链接器会生成 TLSDESC 重定位。
  • [实跑] CGO_ENABLED=0 出不了 c-shared（导出符号需要 import "C"）；openharmony 上 net 包依赖 cgo，所以不能加 -tags netgo。

2. 先例

  • 思源笔记鸿蒙版 siyuan-harmony [源码]：Go 内核编成 libkernel.so，napi_init.cpp 用 std::thread 调用导出的 StartKernel，内核监听 127.0.0.1:6806，Main.ets 里的 Web 组件用 loadUrl 加载；开了 MixedMode.All 和 ohos.permission.INTERNET；deviceTypes 包含 phone / tablet / 2in1。要注意它用的是官方 Go + GOOS=android，再手工补丁 TLS。
  • Hey（鸿蒙 VPN） popsiclelmlm/Hey [源码；真机结论为作者自述]：作者称在 HarmonyOS 6.1 真机上实测，GOOS=android 编的 Go .so 在外来线程会 SIGSEGV；换成 star4277 v1.26.5-beta1 + GOOS=openharmony（TLSDESC）后正常。他用 NDK clang 编 libxray / libsingbox / tun2socks，在 macOS 上用 DevEco + hvigorw 构建，细节见其 docs/harmonyos-go-tls-wall.md 和 docs/building-native-cores.md。这里的真机结论是作者自述，未经复现。
  • gomobile 没有官方的鸿蒙支持。

3. NAPI 接入

以下内容 [源码，取自上述两个工程]：

  • CMakeLists：add_library(entry SHARED napi_init.cpp)，target_link_libraries(entry PUBLIC libace_napi.z.so libapp)；预编译好的 .so 放在 entry/libs/arm64-v8a/，用 IMPORTED 方式引用。
  • 用 napi_module_register + constructor 注册模块；调用 Go 要放在独立线程里（std::thread 或 napi_create_async_work）。
  • 一个坑（Hey 的记录，未复现）：Go .so 加载之后不要再 setenv，会崩；环境变量要在首次 dlopen 之前设好。
  • [摘要] 开启代码签名后，只有随 HAP 一起打包签名的 libs 下的 .so 才能加载；不能 exec 独立的 Go 二进制（W^X）。这一条来自搜索摘要，没有核实。

4. ArkWeb 与本地服务

  • 最省事的做法：App 内 Go 监听 127.0.0.1，ArkWeb 里 loadUrl("http://127.0.0.1:端口/")，需要 ohos.permission.INTERNET（思源的实例就是这么做的）。如果遇到明文 HTTP 被拦截，可以配置 network security config 的 cleartextTrafficPermitted，但这一条来自论坛资料，不是官方原文。
  • 不走 HTTP 的备选 [官方文档]：onInterceptRequest、customizeSchemes / SchemeHandler 自定义协议、javaScriptProxy 走 NAPI。参考：web-scheme-handler。

5. 打包签名

以下内容 [官方]：

  • 不一定需要 DevEco Studio：Command Line Tools（含 hvigor / ohpm / hdc，需要 JDK 17 / 21）就够，ohpm install --all 之后用 hvigorw assembleHap --mode module -p product=default -p buildMode=debug --no-daemon 构建，macOS / Linux / Windows 都可以。参考：命令行构建应用。
  • 调试证书和 Profile 在 AppGallery Connect 申请，绑定设备 UDID，需要华为开发者账号；安装用 hdc install -r xxx-signed.hap；鸿蒙 PC 的 deviceTypes 写 2in1。

完整链路

  1. 在 Linux 构建机 / 容器里编译 star4277 v1.26.5-beta1 工具链：cd src && GOROOT_BOOTSTRAP=... GOTOOLCHAIN=local bash make.bash。
  2. 把 Go 入口改成导出库：//export StartServer 返回端口，保留 embed 和 net/http。
  3. 用前面的命令编出 libapp.so，放进 entry/libs/arm64-v8a/，再用 llvm-readelf 确认重定位里只有 TLSDESC。
  4. 用 DevEco 的 Native C++ 模板写 NAPI 胶水，在线程里调用 Go，并在加载前设好环境变量。
  5. ArkTS 页面拿到端口后 loadUrl；加上 INTERNET 权限和 2in1。
  6. hvigorw assembleHap → 签名 → hdc install。

需要强调：这条链路的第 1～3 步在 Linux 上有 [实跑] 的依据（且仅限模拟环境），第 4～6 步目前只有 [源码] / [官方] 层面的依据，没有在真机上走通过。

风险与备选

风险

  • 工具链是个人维护的 fork，版本锁在 1.26.5；
  • 真机上的信号处理、线程限制、W^X 都还没验证；
  • 调试签名依赖 AppGallery Connect 账号；
  • 思源和 Hey 两个先例的 TLS 处理方式并不一致（一个是官方 Go + android 手工补丁，一个是 openharmony fork + TLSDESC）。

建议的第一步：先在真机上装一个最小 demo HAP，验证 dlopen + HTTP + ArkWeb 这条链路。这一步通了，后面才有意义。

备选方案

  • Go 编成 wasm，跑在 ArkWeb 里；
  • 后端用 ArkTS 重写；
  • 核心换成 Rust（有 aarch64-unknown-linux-ohos 目标）；
  • 或者退回到在 HiShell 里跑 Go 命令行（钉钉 dws 有先例）。
