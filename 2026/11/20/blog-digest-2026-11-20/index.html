1. How OpenAI’s Performance Factory keeps ChatGPT fast

来源：https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast
日期：2026-11-19

核心概要

这篇文章讲的不是又一个 agent demo，而是 OpenAI 已经在生产里跑了三个多月的性能工程产线。为了让 ChatGPT 的延迟和可用性跟得上产品迭代，他们做了 Performance Factory：在云端用 Codex 和自家模型，把性能回归从告警调查、根因、提交修复，做到上线后再对照基线验证。第一套工作流 Regression Workflow 跟踪了 1700 多次调查，根因超过 600 起，大约每天 17 次自动调查。数字本身比口号有用，也给后面的“还不完美”留了对照。

演进路径写得很清楚，几乎是一份“agent 如何从助手变成产线”的说明书。Codex 之前，调查全靠人手翻指标、对比 trace、登机器、读代码，团队为此攒了 30 多种性能工具。Codex 成为搭档后，不熟系统的人也能问“为什么变慢了”，但还得人来选工具、带节奏。再往后，他们把调查过程收进共享 skill perf-forensics，用历史回归做 eval，可以只给一条告警就跑完诊断。然后出现了“人肉中转”：工程师把告警粘进 Codex，再把结论粘回 Slack。再自动化一步，告警会在云端直接拉起 Codex 并回帖，但写修复和验证恢复仍靠人，Slack 线程一多，连“该看哪条回归”都成了负担。最后才是工厂：任务带着状态和发现在 agent 与工程师之间交接，一项回归从调查一直走到生产恢复验证；常见优化也可以做成定期跑在各服务上的工作流，一个工作流发现优化后，还能在另一个工作流里开任务去验证和落地。

系统拆成四块：可配置工作流的任务服务（状态、允许转移、哪些步骤必须有人，以及每步的 Markdown prompt）、周期性把就绪任务派给 agent 的 dispatch loop、在内网云环境里程序化调用 Codex 的 API（能访问代码仓库，以及指标、日志、trace、CPU profile、内存快照），以及等 GitHub review 或部署完成后再把任务唤醒的订阅。agent 以服务身份运行，权限可收束，也不再依赖工程师笔记本开着。Regression Workflow 的阶段是 needs investigation → root caused → fix proposed → resolved，人只卡在 Review & deploy。调查时 agent 会回溯指标何时开始变差（告警往往晚了几个小时），并区分“同类请求变慢了”还是“慢请求变多了”，再对照部署和 feature flag，用日志或 trace 检验代码能否解释现象。为了对付“找到第一个说得通的解释就停”，他们加了对抗式审查：另开一个 Codex 会话专门证伪。文中的例子是，调查 agent 把失败的 ChatGPT 会话归到图片下载错误，审查者发现负责定位文件的内部服务已经恢复、图片请求却还在失败，于是重开调查。人工抽查 100 条根因建议，约 70% 准确，30% 还需要补证据或没真正建立因果。

修复比找根因更难。agent 的改动有时过于复杂，或引入新问题；加缓存这类方案还会碰到过期数据等架构权衡，需要熟悉服务的工程师拍板。修复提案同样过对抗审查。任务报告会自动汇总影响、根因和方案，并配上指标时间序列、CPU flame graph 和 trace，方便人扫一眼再决定是改 PR、自己重写，还是留评论让工作流再唤醒 agent。修复上线后，agent 对照原先基线验证；只恢复一部分就关掉原任务、为剩余变慢新开任务（可能是别的原因）；完全没改善则记下来，打回重新调查。他们还在用“agent 提案 vs 工程师最终合并”做改进循环，并探索用合成性能测试先自测，以及让低风险修复最终无人值守合入。文章承认，今天的瓶颈常常已经是等工程师 review 和合并。

关键洞察

  • 先把人从中转里拿掉，再谈端到端：从 skill、到粘贴代理、到云端自动调查、再到带状态的工厂，每一步都是因为上一步的人手成了瓶颈，而不是一上来就设计工厂。
  • 任务状态必须活在单次会话之外：发现、进度和订阅事件都记在任务上，code review 或部署之后才能换一个 agent 接着干；只把结论丢在 Slack 里，规模一大就无法交接。
  • 对抗式审查是准确率的关键机制：另开会话证伪，而不是同一个 agent 再检查一遍。70% 的根因准确率说明没有这层检查会更糟，图像下载那个误诊也是靠审查才被拦住。
  • 修比重，人还在关键决策上：修复质量、架构权衡和合入仍是短板；文章自己也说，今天最慢的可能是等工程师 review。合成测试和无人合入都还在探索。
  • 改 agent 要像改线上服务一样做回归：用历史事故做 backtest，调查能力和给工程师看的摘要分开评；还要注意指标过期、恢复后的证据、以及 agent 记忆泄题。工具故障、权限缺失也要纳入自我修复，否则调查会 silently 失败。

评价

优点：少有的把“agent 工厂”从演进路径、系统拆分讲到生产数据的文章。1700 次调查、600 个根因、70% 准确率，让讨论有了锚点。对抗审查、事件订阅、合并相关事故并按影响排序、带证据的可扫报告，以及用 Performance Factory 修自己的工具故障，都是可以搬到别的领域的做法。对正在把一次性 agent 会话升级成产线的团队，信息密度很高。

不足：Performance Factory 和 perf-forensics 都是内部系统，没有开源，无法直接复用。根因仍有 30% 不准，修复质量更是短板，合成测试和无人合入都还在探索。文章偏“我们做成了什么”，对失败案例和评估细节（分数怎么打、对抗审查的 prompt、误诊如何回流）着墨不多。部分段落仍有产品宣传味道。

适用场景：在生产里用 coding agent 做性能、SRE 或值班自动化的团队；想把一次性 agent 会话升级成带状态工作流的人；以及关心如何评估和约束生产 agent 的工程师。
