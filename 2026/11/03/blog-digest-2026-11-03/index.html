1. Scaling Git at OpenAI

来源：https://openai.com/index/scaling-git-at-openai
日期：2026-11-02

核心概要

OpenAI 的 monorepo 在 Codex 普及后被”并行开发”压垮了：一个工程师同时有好几个改动等 CI，每次 push 又会触发多个任务去 fetch 同一个 commit。文章说从去年年底开始，fetch/push 变慢、merge 失败，可靠性一度跌到 90% 以下。他们的结论不是”Git 不行了”，而是”服务 Git 的方式不行了”，于是在保持 Git 协议和客户端完全兼容的前提下，自研了新后端 Pando，现在承载 OpenAI monorepo 的全部开发。

文章先对比了两种常见的分布式 Git 方案：三阶段提交（3PC，多副本对每个 ref 更新达成多数派）和基于对象存储的共享预写日志（WAL，所有 ref 更新都要 CAS 同一个 manifest）。前者把副本磁盘和通信延迟放在 push 路径上，后者让无关分支的 push 也争同一个协调点，副本还要先读、建索引才能服务。Pando 的做法是放弃两条”默认前提”：一是放弃全仓库一致的 ref 快照，改为因果一致（每个 ref 内部可串行化，跨分支不保证同一时间点）；二是放弃给每个客户端单独生成 packfile，改为直接复用 push 时收到的 pack。

具体实现上：push 时流式校验 pack 并直接写入 blob 存储，不解包到本地仓库，元数据库里记一个”ref version”（新 tip、对应 pack、依赖的旧版本），整个写操作只需 O(1) 次元数据读写，唯一的竞争点是单个 ref 指针的 CAS；新分支 push 时默认只向客户端广告 trunk 一个 ref，保证生成的 pack 能被后续 fetch 直接复用（中位数 pack 不到 20 KiB，P99 不到 3 MiB）；fetch 时把 have/want 映射到 ref version，选出需要的 pack，借助 Git 协议里较冷门的 packfile-uri 让客户端去区域缓存服务 Express 下载，缓存命中率超 99%；后台按 LSM 树思路把 L0 小 pack 逐级合并成 cover（目前到 L4），同时起到类似跳表的作用，让 fetch 规划的复杂度降到对数级。

结果方面，文章给出：push 中位延迟降低近 80%（文中另一处说法是近 5 倍），每天交付接近 1 PB 的 Git 数据，单小时峰值超过 57 TB，普通云主机上 clone/fetch 能跑满 10 Gbps。项目用 Codex 从立项到上线只用了 10 周，Rust 实现，配了一致性测试套件和确定性仿真测试，还让模型写 Lean 和 TLA+ 来形式化验证。部署上先做读写透传代理和旧系统并行，再分批迁移客户端，并把对 packfile-uri 等的改进贡献回上游 Git。

关键洞察

  • 一致性是可以按业务需求降级的：用户和 agent 实际只关心”单个分支的更新顺序”，并不关心全仓库 ref 的全局顺序。把一致性模型收窄到 per-ref，就把全仓库的写竞争变成了单 key 的 CAS。这是这篇文章最值得借鉴的思路，适用于很多”默认要全局一致、实际不需要”的系统。
  • 用”多传一点”换”可复用”：只广告 trunk 会让客户端 push 的 pack 偏大、可能有冗余，但换来的是同一个 pack 能原样服务所有后续读者，服务端几乎不用算。读多写少、读者高度重复的场景里，这笔账非常划算。
  • 善用协议里的冷门能力：packfile-uri 让服务端只做协商、把字节搬运交给 CDN 式缓存，从而计算和带宽可以独立扩展。在做兼容性改造前，先通读协议的扩展点往往能省下大量魔改。
  • LSM 式压缩一举两得：多层 pack cover 既提高压缩率，又充当索引加速 fetch 规划，而且旧层不做 GC、各层都参与服务，这个设计对任何”追加写 + 增量同步”的系统都有参考价值。
  • agent 驱动开发的工程配套：10 周上线的前提是一致性测试、确定性仿真、形式化验证这些”让 agent 能自己验证对错”的基础设施，以及用 skill 让 Codex 帮团队完成迁移。这比”agent 写了多少代码”更有启发。

评价

优点：讲清了问题来源（agent 带来的并发量）、方案对比（3PC 与 WAL 的瓶颈分别在哪）、自己的取舍和代价（跨分支读不一致、堆叠分支 push 变大），并给出生产数据。原文还有交互式模拟器对比三种架构，教学价值很高。兼容 Git 协议、向上游贡献改进的路线也比另起炉灶更务实。

不足：Pando 本身没有开源，文章只说在探索如何分享相关技术；模拟器是”教学模型而非生产基准”，三种方案的对比带有作者自己建模的成分，3PC 和 WAL 也都是他们”建模的版本”，不代表业界最优实现。部分数字口径（近 5 倍与近 80%）不统一，且对元数据库、Express 等组件的选型只点到为止。关于用新模型做形式化验证、红队的部分偏宣传，细节很少。

适用场景：维护大型 monorepo 或自建 Git 托管的基础设施团队；正在为 agent 并发开发做准备、担心 CI 与源码系统扛不住的团队；对分布式系统一致性取舍、缓存与压缩设计感兴趣的工程师。小团队或用 GitHub/GitLab 托管的普通仓库，主要是开阔视野，短期内用不上。

推荐指数：⭐⭐⭐⭐ (4/5) — 架构取舍讲得非常透，”按真实需求放宽一致性 + 复用 pack”的思路通用性强，值得精读；扣一星是因为系统未开源、对比基于自建模型，对多数读者的直接可落地性有限。
