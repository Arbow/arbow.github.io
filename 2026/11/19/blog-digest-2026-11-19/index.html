1. Inside the Codex sandbox

来源：https://openai.com/index/inside-the-codex-sandbox
日期：2026-11-18

核心概要

这篇文章把 Codex 的本机沙箱讲清楚了：OpenAI 采用 defense in depth，训练和对齐管“模型愿不愿意做坏事”，沙箱管“就算做了也碰不到什么”。因为 Codex 最常见、也最危险的动作就是在你电脑上跑命令，他们没有把计算搬进虚拟机或 容器，而是用各平台原生隔离机制，直接限制命令在用户现有环境里的文件系统和网络访问。用户通过 permission profiles 配置这些边界。

设计选择很务实。开发者笔记本往往是一套随手改过的环境，复刻进 Docker 成本高，有些工作流还依赖宿主机工具。文章举了在 Mac 上做 iOS 开发的例子：容器里跑不了原生工具链和模拟器；若把构建“委托”给宿主机，那段又跑出了容器沙箱，还得另做限制。所以他们押注 OS 级沙箱，并用一套跨 macOS、Linux、Windows 的 API（命令 + permission profile，需要时再加网络代理）把平台差异藏起来。子进程会继承约束，即使原进程退出后仍活着的后代也不例外。

默认的 :workspace 画像是“能干活，但偏保守”：工作区内可写，但 .git 和 .codex 只读，避免直接改 config.toml 或 .git/hooks；读权限却很宽，因为编译器、SDK 通常在仓库外面——代价是机器上含 API key 的配置也可能被读到；网络默认关闭，能挡住直接外传，同时也会挡住下载依赖。文章自己举了一个很扎心的残留风险：agent 往常被 gitignore 的 node_modules/prettier 里注入恶意代码，编辑器保存时在沙箱外执行，git status 还看不出来。沙箱限制的是访问范围，不是意图本身。企业侧的搭配建议见 Codex security cookbook。

中间大部分是可配置性与实现。config.toml 里可用命名 profile 扩展 :workspace（read / write / deny，:workspace_roots 会把相对路径套到每个 workspace）。网络有三种：全关、全开（:danger-full-access），或走代理按域名放行。配置可分层合并，管理员再用 requirements.toml 的 allowed_permission_profiles 直接禁掉危险选项。模型可以在单条命令上申请额外权限，甚至 require_escalated 要求出沙箱，但由 harness 决定——可能问用户，或交给 auto-review。codex sandbox 还把这套机制从 agent 会话里拆出来，文章用给 @modelcontextprotocol/server-memory 套沙箱当例子：Codex 默认并不隔离 stdio MCP 进程，这一点很容易被忽略。

实现上，共享的 codex-network-proxy 同时开 HTTP 和 SOCKS5，注入 HTTP_PROXY、PIP_PROXY 等变量；域名未获准前先不解析 DNS，避免主机名本身泄密（宽泛通配或直接访问 DNS 服务仍可能被用来外传）。平台层各不相同：macOS 走已标记 deprecated、但仍被 Chrome 使用的 Seatbelt / sandbox-exec；Linux 是 bubblewrap 加 seccomp-bpf，并自带一份 bwrap（有的发行版默认关掉用户命名空间，只给系统 bwrap 开例外），网络命名空间里再通过文件描述符把 loopback 监听器交给沙箱外的 bridge 去连代理；Windows 正在从他们年初那套方案迁到微软的 MXC，主要是为了摆脱提权、慢 ACL，以及留在主机上的防火墙规则和沙箱用户等残留状态。

关键洞察

  • 默认策略是权衡，不是安全边界：宽读、禁写 .git / .codex、默认断网，是为了“能编译”同时挡住最常见的外传；密钥文件可读、对 node_modules 的投毒，文章自己都承认还在。
  • 权限提升必须由 harness 裁决：模型可以请求更多权限或出沙箱，但请求不等于授权；真正落地的是用户确认或 auto-review。
  • 沙箱要能离开 agent 会话单独用：codex sandbox 让同一套 profile 可以罩住 MCP 等默认不受控的进程，否则“会话内很严、旁边进程全开”只是假安全感。
  • 网络策略要做在 DNS 解析之前：即便允许列表本身，主机名也可以变成隐蔽信道；代理放行后再解析，比先查 DNS 再拦截更干净。
  • “在用户本机隔离”比容器更脏，必须跟 OS 能力绑定：Linux 的网络命名空间加 FD 桥、Windows 迁 MXC、macOS 继续赌已 deprecated 的 Seatbelt，都说明统一 API 才是可维护的关键，底层无法一套方案打天下。

评价

优点：少有的把 agent 本机沙箱从产品默认、配置模型讲到三平台实现细节的文章，而且对默认策略的缺口写得很诚实。codex sandbox 和企业 requirements 说明他们把沙箱当成可复用原语，而不只是 Codex 内部实现。对做 coding agent 或要在企业里收紧权限的人，信息密度很高。

不足：叙述大量依赖文中的代码块和示意图，单独抽出原则后，完整的 SBPL / MXC JSON 仍不好直接照抄。Seatbelt 已被官方标记 deprecated；Windows 的 MXC 方案还在迁移，且只覆盖兼容机型。默认宽读对密钥几乎没有防护，要靠用户自己收紧 profile；deny glob 也只在启动前展开，命令运行期间新出现的匹配路径不会自动纳入限制。

适用场景：做 coding agent 或本机工具调用沙箱的工程师，要给企业落地 Codex 权限策略的管理员，以及想给 MCP 或自建工具套同一套隔离的开发者。

推荐指数：⭐⭐⭐⭐ (4/5) — 工程细节扎实、权衡写得诚实，对做 agent 运行时隔离几乎是必读级材料；但默认策略仍有明显缺口，Windows 方案尚未完全落地，所以不到满分。
