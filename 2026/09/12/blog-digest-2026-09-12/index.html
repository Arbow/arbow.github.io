今日新增 1 篇，来自 OpenAI Engineering：他们首次系统性公开了 ChatGPT 背后的在线存储平台 Habitat 的演进史。对做存储、后端架构或正在纠结”Python 撑不撑得住”的工程师来说，这是一篇少见的把取舍逻辑讲透的实战复盘。

1. Rapidly scaling online storage to serve over 1 billion ChatGPT users

来源: OpenAI Engineering
链接: https://openai.com/index/scaling-storage-one-billion-users-part-one
发布日期: 2026-09-11

核心概要

这是 OpenAI 在线存储系列的第一篇（共两篇），主角是 Habitat——支撑 ChatGPT 登录、会话、Codex 设置等所有产品数据读写的在线存储平台。数字先摆出来：每秒 7000 万+ 请求、每周服务 10 亿+ 用户、管理 500 PB+ 数据、覆盖近 40 个地理区域。而它在 2024 年年中的起点，只是一个连单个数据库的 Python 客户端库。

文章的核心叙事是三次关键演化。第一是”库变服务”：2025 年年中，客户端库模式下任何协议变更都要协调几十个服务分批发布，文中给了一个极其生动的失败案例——为降低单区域故障爆炸半径做的分片迁移，光发布就耗时数天，加 shadowing 又几天，修 bug 再几天，最后开 flag 时某个团队回滚服务到旧的有 bug 的客户端，反而造成了他们拼命想避免的故障。把存储逻辑收拢为独立服务后，部署、可观测性、安全策略（访问控制、审计日志）都有了单一控制点，这也是集中式数据安全防线的关键：Habitat 是防御外部、内部乃至 agent 访问的核心卡口。

第二是”明知 Python 会到极限，仍然先用 Python”：作者很坦率地称之为”战略性技术债”——当时的第一目标不是资源效率，而是解除产品开发者的阻塞、稳住平台。更妙的是一个双保险式的赌注：他们赌自家模型进步到需要全面重写时，Codex 和 GPT 能让迁移变得可行。这个赌注后来兑现了——2026 年 Q2，2 名工程师带着 Codex 和 GPT-5.5 把整个服务重写为 Rust，如今承接 95% 生产流量，CPU 效率 6 倍、内存效率 15 倍，Python 峰值曾扛到每秒 2000 万请求后即将完全退役。

第三是 Python 时代的大量尾延迟实战经验，构成了全文技术上最有价值的部分：asyncio 调度延迟（而非下游存储）才是 p99 的主导因素，他们通过周期性调度背景任务并记录”预期与实际执行时间之差”来实时测量事件循环延迟；Statsig 特性开关每分钟无 jitter 全量轮询解析大 JSON，叠加每 pod 8 个 Python 进程，导致每分钟全体 worker 周期性卡顿；aiohttp TCPConnector 默认 LIFO 连接复用在突发流量下会把更多新请求导向返回连接最晚（即最慢）的进程，形成亚稳态故障（metastable failure），改 FIFO 打破正反馈环后才恢复；最后用 Envoy 做 HTTP/1→HTTP/2 升级和连接 fan-in，把下游 Cosmos DB 的连接数从一个数量级压到个位数。

关键洞察

  • “库 → 服务”的转折点信号：当客户端库的变更需要协调几十个服务滚动发布时，运维扇出本身就是最大的故障源。单一控制点的价值（部署、观测、安全策略集中）会在这个时刻超过服务化引入的额外一跳延迟。
  • 技术债可以”战略性”地背，但要配上对冲：明知 Python 撑不到 100x 仍然先用，理由是当下更紧迫的是解锁业务；同时对冲手段是赌自家 AI 编码模型会把未来重写的成本打下来——这个赌注用 2 人 + Codex + GPT-5.5 完成 Rust 重写兑现，堪称”用 AI 还技术债”的标杆案例。
  • Python 高并发服务的真正瓶颈是事件循环调度延迟：asyncio 只给并发不给 CPU 并行，路由、压缩、加密、校验和这些 CPU 活会让已就绪的响应在队列里干等几百毫秒甚至数秒。解法反直觉：单进程只服务极少量并发请求，靠横向堆 worker 进程数量换吞吐。
  • 连接池 LIFO 复用会制造亚稳态故障：慢服务器返回连接最晚 → 被 LIFO 优先复用 → 新请求继续涌向慢服务器，正反馈直到重启才能解。一个字符的改动（LIFO→FIFO）打破循环。这是 Meta 那篇 metastable failure 论文在 Python aiohttp 上的具体复现。
  • API 设计即扩容策略：Habitat 刻意只暴露 TAO 风格的受限 NoSQL API，拒绝任意 SQL——因为”写起来便宜、跑起来昂贵”的查询是扩容的天敌；复杂查询需求通过 CDC → Rockset 离线视图作为逃生舱，把分析与在线负载隔离。

评价

优点：信息密度极高且罕见地诚实——不是”我们如何用十年建成伟大系统”的叙事，而是”我们如何在三年 10x/年的狂奔中连续做出正确排序”的复盘。LIFO 连接池亚稳态故障、Statsig 配置轮询卡顿这些细节是一线踩坑才写得出来的，对任何运行 asyncio 服务的团队都有直接抄作业价值。”战略性技术债 + AI 对冲”的决策框架，可能是比具体技巧更有普适性的收获。

不足：结构上略有广告色彩——Python→Rust 的重写和 6x/15x 效率数字给得很提气，但重写过程本身只字未提（ promised 到 future blog），对”AI 辅助大规模重写到底怎么做”的读者来说是最吊胃口的留白；多租户可靠性、读优化、Cosmos DB 合作这些硬核内容全部推迟到下篇，本篇单看像一篇加长版预告。另外整套方案深度绑定 Azure Cosmos DB 和 Envoy/Istio 生态，非同栈团队可借鉴的是思路而非方案。

适用场景：正在做存储中间件/数据平台选型与演进的架构师；用 Python asyncio 撑高并发、被尾延迟折磨的后端团队；以及想参考”什么时候该把客户端库升级成服务”的任何平台组。

推荐指数：⭐⭐⭐⭐⭐ (5/5) —— 题材稀缺（一线超大规模存储平台的完整演化复盘）、细节可信（具体到 aiohttp 连接复用策略这种颗粒度）、且”2 工程师 + AI 完成核心服务 Rust 重写”是今年最值得记住的工程事件之一。唯一保留是部分内容预告到了下篇，但本篇独立成章的信息量已完全值回时间。
