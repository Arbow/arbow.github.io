今天只新增一篇，但分量够重：Armin Ronacher（Flask、Jinja、Ruff 等项目的作者）时隔四年重启了自己 2022 年的实验性序列化库 Deser，写了一篇长文正面挑战 Rust 生态里地位近乎”王座”的 Serde。这不是又一篇”我重写了 X”的自嗨文，而是一份非常坦诚的设计复盘——包括新架构付出了什么代价。

Deser: Rethinking Rust Serialization

来源：https://lucumr.pocoo.org/2026/9/29/deser/（Armin Ronacher，2026-09-29）

推荐指数：⭐⭐⭐⭐⭐ (5/5) — 对任何写 Rust 的人都是必读：它把 Serde 那些你大概率踩过、却只能绕着走的”设计税”一次性摊开讲透，并且用一套完整可跑的替代实现证明了”换一套架构能换来什么、又要付出什么”。设计权衡的论述质量本身就值得学习。

核心概要

文章从三个具体的 Serde 边角案例切入，每个都是”特性之间的不良交互”而不是简单的 bug：

  1. “数字变成了 map”：内部 tagged enum 遇上 serde_json 的 arbitrary_precision 特性时直接反序列化失败。根因是 Serde 数据模型没有任意精度数字的位置，serde_json 只能用带 magic key 的 map 做”带内信号”（in-band signalling），而这个魔法 map 在 enum 的字段缓冲区里不被识别。更糟的是 Cargo feature 统一合并——依赖图里任何一 crate 打开该特性，你就中招。
  2. flatten 弄坏整数 key：HashMap<u32, u32> 单独解析正常，一旦被 #[serde(flatten)] 包一层就报错——因为 flatten 需要先缓冲值，缓冲时 "42" 只是字符串，类型驱动的整数转换已无机会发生；且错误位置指向文档末尾而非出错处。
  3. 适配器无法组合：deserialize_with 接受函数而非类型，函数不能当类型参数，所以没法把 from_hex 应用到 Option / Vec 内部，只能为每层包装手写变体，还容易忘了加 #[serde(default)]。

Ronacher 的判断很明确：这些都不是能轻易修的 bug，而是 Serde 设计的自然推论，且被其稳定性承诺”锁死”。他总结了 Serde 三个根源性决策：一套 trait 服务所有格式（自描述格式与非自描述格式混用，部分特性只在部分格式可用，还有派生 struct 静默接受 JSON 数组这类怪癖）、缓冲即丢失信息的固定数据模型（tagged/untagged enum 和 flatten 都要缓冲，缓冲区装不下格式层知道的一切）、调用栈递归（嵌套深度吃栈空间，需递归限制兜底，且反序列化无法暂停等待更多输入）。

Deser 的答案是把控制流反过来：学 dtolnay 的 miniserde，不再由类型驱动、递归回调 visitor，而是格式层发事件、类型提供 sink，嵌套时把新 sink 交还给一个把全部状态放在堆上（arena）的 driver。由此得到：无栈溢出（嵌套深度独立于栈空间，用 layer 自选限制）、可暂停可跨线程的流式反序列化（对 tokio 友好）、可扩展的数据模型（DateTime、Uuid、bytes 等作为扩展值，带降级回退，不再靠 magic key 走私数据）、无损缓冲（tag 在后的 enum 缓冲后错误位置、协议扩展信息全部保留）、以及原生的零缓冲 flatten。XML 一节是差异的极端展示：Deser 按命名空间匹配元素、跨间隔收集同名子元素进同一个 Vec、untagged enum 缓冲后信息不丢；而 Serde 生态最流行的 quick-xml 忽略命名空间、靠全局 feature 缓冲，套一层 untagged enum 后甚至静默丢数据。

关键洞察

  • “修不了”比”有 bug”更值得警惕：Serde 的三个案例没有一个是实现错误，全是设计推论，再被稳定性承诺和 orphan rule 固化。评估一个核心依赖时，要区分”可以等的 bug”和”结构性的、等不来的修复”。
  • 带内信号（magic key）是数据模型表达力不足的症状：arbitrary_precision 和 TOML datetime 都靠 map 加魔法键走私类型信息，一旦和 enum 缓冲等特性交互就会炸，且 Cargo feature 全局合并让触发面不可控。扩展值 + 降级回退是更干净的解法。
  • 缓冲是有损的：任何”先缓冲再决定”的特性（tagged/untagged enum、flatten）都是错误信息和协议细节的丢失点。Deser 的”记录事件+元数据”的无损缓冲值得所有做数据管道的人参考。
  • 适配器应当是类型而不是函数：函数不能当类型参数，所以永远组合不起来；as = Option<Vec<DisplayFromStr>> 这种写法把组合性还给了用户，验证器（Check<NonEmpty, ...>）也统一进同一套适配器体系。
  • 非自描述格式（protobuf、bincode）被主动排除在外：这是”修 Serde”必须付出的妥协之一。想在一个维度上做得更好，就得明确定义自己不做什么——反面是”一套 trait 通吃所有格式”的复杂度。
  • 性能与体积代价被如实公开：JSON 读取平均慢约 10%（区间 -33%~+60%），写入互有胜负，二进制体积膨胀明显；换来的是 release 派生代码编译快约 2.3 倍、无栈溢出、可流式暂停。作者甚至承认内部用了 unsafe 来把借用 sink 链放上堆。

评价

优点：问题定义极其扎实——三个案例全部可复现、可解释到机制层面，不是情绪化吐槽；解法与代价并陈，性能数字、unsafe 使用、”它不是 Serde”这条最大代价都直接写明；XML/TOML datetime 的对比案例信息密度高，读完对”数据模型表达力”这个抽象概念有了具体体感；生态现状判断清醒（orphan rule 使替换 Serde 几乎不可能，Deser 的目标是把格式覆盖补齐到”不因格式而劝退”）。

不足：Deser 仍是 0.x 实验项目，作者自己都未宣称生产可用；性能混合、二进制膨胀、内部 unsafe 都是实打实的门槛；生态上 derive 属性、第三方适配器、社区资料与 Serde 差距巨大，短期内只适合个人项目或特定场景（如处理海量不可信 JSON、深嵌套、XML 重度用户）。

适用场景：处理不可信深嵌套 JSON 的服务（需要栈安全 + 流式暂停）、被 Serde XML/TOML datetime 问题折磨过的项目、想学习”如何设计一套反 Serde 的序列化架构”的 Rust 开发者。普通 CRUD 场景继续用 Serde 即可。
