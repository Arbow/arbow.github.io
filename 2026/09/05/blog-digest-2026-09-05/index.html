1. 高效电商 AI 智能体解剖指南（选自 Anthropic 的 Claude 博客）

来源：宝玉的博客（Anthropic 官方博客翻译版）
链接：https://baoyu.io/translations/2026-09-02/the-anatomy-of-effective-commerce-agents
发布日期：2026-09-02
类型：生产实践指南
推荐指数：⭐⭐⭐⭐⭐ (5/5) — 必读。这是目前公开资料里少有的、把 Agent 从架构选型、延迟成本优化到生产运维一条龙讲透的文章，且每条建议都带企业级部署的实测数据背书，不是纸上谈兵。

核心概要

Anthropic 基于过去一年与零售、电商、旅游、娱乐、电信等各行业团队合作上线的电商 AI Agent 经验，写出了这篇系统性的架构指南（宝玉翻译为中文版）。文章的核心论点非常鲜明：这些成功的生产系统共享一个极简架构——把单个模型放进标准 Agent Loop，配上技能（Skills）、工具和评估套件，而不是搞意图路由器 + 一堆领域子 Agent 的复杂分层。

文章分三部分。第一部分讲架构：为什么”单模型 + 技能”持续优于”子 Agent”设计——每次任务交接给子 Agent 都是一次状态有损操作，消耗数倍 Token、增加数秒延迟，而技能指令直接加载进掌握完整历史的主 Agent，零交接成本。子 Agent 只在两种场景值得用：作为工具调用的”深度研究”类垂直任务，或者某个领域已有带独立合规要求的成熟专属 Agent。第二部分攻延迟与成本：提出”延迟预算”概念，兵分两路——缩短端到端绝对延迟（减少轮次、加快工具、急切分发）和降低感知延迟（流式渲染组件、展示思考过程）。第三部分讲生产运维：跨会话持久化记忆的存/写/读三层设计、Harness 层面的安全把关、非确定性系统如何发版。

记忆部分的设计尤其精彩：记忆要存自己的数据库而非模型里，每条事实是结构化小记录（key + value + 分类 + 来源会话）；写入采用异步提取器（独立进程读对话、维护记忆库），比让主 Agent 自己调”保存事实”工具的做法事实召回率提升 13%；读取按人维度而非账号维度（商家账号常多人共享），且必须尊重权限隔离。

关键洞察

  1. 系统提示词 vs 技能的判断标准是使用频率：与三分之一以上流量相关的指令放系统提示词，其余长尾需求做成技能；安全底线、品牌调性、过敏史等关键指令永远待在系统提示词里。
  2. 工具边界会变成”垃圾桶”：当你在工具里手写业务规则（查库存还要串商品目录、门店服务、履约服务），正确解法是在后端建一个能直接回答问题的端点，让工具去调——工具不该替上游系统干活。
  3. 急切分发（Eager Dispatch）：工具参数是流式输出的，Harness 可以在参数一生成完毕就立刻触发调用，把数秒等待压缩到几百毫秒——总耗时不变，但用户感知天差地别。
  4. 提示词缓存的三区结构：全局区块（系统提示词+工具定义，永不变化）→ 会话区块 → 易变区块（时间戳、当前页面）放最末尾。最常见错误是把当前时间挂在系统提示词开头，导致缓存每次被静默击穿。顶级部署缓存命中率可达 90–99%。
  5. 成本要按”完成单次任务”算，不是按单次调用算：便宜的模型如果需要更多轮次或频繁翻车，其实一点都不便宜；测试结果不相上下时果断选高智商模型，因为质量才是留存和采用的驱动因素。
  6. 异步记忆写入同时解决延迟和注意力问题：让主 Agent 自己保存记忆会争夺它的注意力，直接表现为错失该记住的信息；拆分出的提取器只读纯文本对话，还能防止商品描述意外变成”用户事实”。

评价

优点：内容密度极高，几乎每一段都能直接落地；大量企业实测数据（13% 召回率提升、90–99% 缓存命中率、1.5–2 倍缓存读取加速）让建议有说服力；”延迟预算””感知延迟”的拆分框架对任何面向 C 端的 Agent 产品都适用。

不足：所有经验都绑定 Claude 生态（Agent Skills、Claude Agent SDK、prompt caching 的断点机制），换到其他模型家族需要自行等价映射；评估发版部分相对单薄，没有展开讲 eval suite 具体怎么建。

适用场景：正在构建面向消费者/商家的 Agent 产品的工程师与技术负责人；也在做单 Agent + 技能架构选型决策的团队；任何想优化 Agent 生产成本与延迟的人。即便不做电商，第二、三部分的缓存与记忆设计也是通用的。

2. 从 Expected Return 到 Surrogate Loss：RL 如何接入 Backprop

来源：李乾坤的博客
链接：https://qiankunli.github.io/2026/09/02/rl_gradient_estimation.html
发布日期：2026-09-02
类型：技术教程 / 概念澄清
推荐指数：⭐⭐⭐ (3/5) — 参考。写法清晰、概念纠偏到位，但对已经熟悉 policy gradient 的读者信息增量有限，更适合作为给同事解释”为什么 RL loss 长这样”时的引用材料。

核心概要

这是一篇 4 分钟的短文，回答一个看似基础却经常被含糊带过的问题：强化学习用 expected return 描述”什么是更好的策略”，神经网络训练却要求一个可微的标量 loss——两者之间的桥是怎么搭起来的？

文章先澄清一个常被误解的点：backprop 本身不是学习算法，它只负责求导（differentiation），求出的梯度还要交给 optimizer。接着指出 RL 目标函数无法直接 backprop 的两道坎：其一，数据分布随参数一起动——轨迹概率 P(τ;θ) 里带着 θ，参数一更新，上一轮采的数据就”过期”了，这正是 on-policy 困境的数学根源；其二，采样操作不可导，”从分布里掷骰子抽动作”就像在计算图正中间插了个 np.random.choice，链式法则在此断裂。

关键的概念区分在于：监督学习是 target-based supervision，label 和 prediction 在同一预测空间可以直接相减定义残差；RL 是 evaluative feedback，Reward 只评价行为”有多好”，不指出正确答案是什么。所以 policy loss 本质上是 surrogate loss 而非 prediction error——策略梯度不计算 ∇R，而是用 Reward/Advantage 加权已采样动作的 log-prob 来估计期望 Reward 的梯度。最后顺着 log-derivative trick 从 gradient estimator 推到 REINFORCE 的参数更新。

关键洞察

  1. Backprop 只负责 differentiation：把”求导”和”学习”分开理解，很多 RL 与监督学习的表面差异会自然消解——两者的差异在 loss 的构造，不在求导本身。
  2. On-policy 困境的数学根源：P(τ;θ) 带着参数 θ，意味着训练数据分布随优化过程漂移——这不是工程妥协，而是问题定义内生的。
  3. 采样是不可微算子：梯度流到离散采样处就断了；softmax 的平移不变性（logit 绝对高度无意义）也顺带解释了”权重绝对大小不重要、相对差值才重要”。
  4. Surrogate loss ≠ prediction error：Reward 是效用空间的标量评价，不是行为空间里的 ground truth target；理解了这一点，就理解了为什么 PPO/GRPO 这些算法要绕这么多弯。

评价

优点：概念拆解干净利落，”数据分布随参数漂移”和”采样不可导”两道坎的提法直击要害；适合作为从监督学习思维迁移到 RL 思维的解毒剂。

不足：篇幅短，止步于 REINFORCE，没有触及 variance reduction、off-policy correction、PPO 的 clipping 等现代实践必经之路；对大模型 RLHF 场景的衔接也只是点到为止。

适用场景：刚从监督学习转向 LLM 后训练（RLHF/GRPO）方向、需要建立 policy gradient 直觉的工程师；或团队内做概念分享时的基础参考。
