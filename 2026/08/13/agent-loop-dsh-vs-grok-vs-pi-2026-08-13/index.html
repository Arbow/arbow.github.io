Agent 循环对比: deepseek-harness vs grok-build vs pi-mono

一句话概括

项目 本质
deepseek-harness 严格的事件溯源 (event-sourced) React 循环 —— 会话日志 (log) 是核心骨架，LLM 历史记录从日志中派生而来；有四个经过类型定义、基于作用域过滤的 agent/* 扩展点；插件化架构，循环本身不直接修改。
grok-build Actor 模式 + 分层 turn 循环 (Rust/tokio)，一个迭代式循环内嵌于一个响应式 session actor 中；通过 hooks/plugins/marketplace/skills/MCP 进行扩展；在基础循环之上拥有一个独特的 goal-tracker 元代理。
pi-mono 极简的顺序流 ReAct 循环 (~420 行)，一次模型调用 + 顺序执行的工具调用；所有重要功能（压缩、重试、权限、持久化）都存在于 AgentSession 之外的循环外部；以人为本的转向/跟进队列是其亮点。

deepseek-harness Agent 循环的独特特征

综合对比，deepseek-harness 的 Agent 循环在设计上具有以下独特点：

  1. 事件溯源作为核心骨架 —— 这是其他两者都没有的。LLM 历史记录是 deriveMessages() 从类型化接口中对 SessionEvent 日志的纯投影。grok 和 pi 将消息存储为数据；dsh 将事件存储为数据并派生消息。这使得分叉/恢复/压缩在结构上是安全的，而非临时性的。

  2. 运行时强制执行的不变量 —— invariant.ts 断言每个循环构建的请求都等于日志派生。这主动捕获了 “日志重构不同步”，是其他两者缺乏的安全网。

  3. “插件而非循环修改” —— 只有 4 个类型化的扩展点，经过作用域过滤和调度融合。相比 grok 的 hook 脚本/turn-hooks/marketplace/skills/MCP/custom-agents 层叠，这是一种更教条（狭窄但一致）的可扩展性策略；相比 pi 的功能 hooks 更类型化。

  4. 工具分发重叠但保持模型排序 —— 带有 commitReady() 跨连续模型顺序槽位推进的边界池是独一无二的。grok 在并行池中序列化同文件；pi 不并行化。

  5. 能力接缝 (Service Definition/Provider/Consumer) —— 每个横切关注点 (shell, fs, subagent, compaction, web, llm) 是一个三角色接缝，核心中”从不只有一个角色”。grok 和 pi 将这些折叠进循环/harness 代码中。

  6. 代码模式 —— 将工具作为生成的 SDK 暴露在单个 run_code 传输后，这是三者中独有的。

deepseek-harness 的权衡: 哲学上的纯粹性 (日志作为真理、类型化接缝、不变量) 以牺牲接入复杂性为代价换来确定性。grok 的优势在于丰富的产品表面 (目标追踪器、内存/dream、doom-loop 检测、LLM 权限分类器)。pi 的优势在于最小的核心循环简单性和以人为本的转向人体工程学 + git 风格的会话树。
