1. Warp 如何让 Agent 自我进化

来源：宝玉的博客
链接：https://baoyu.io/blog/2026-08-28/warp-self-improving-agents
发布日期：2026-08-28
推荐指数：⭐⭐⭐⭐ (4/5) — 推荐阅读

核心概要

这篇文章是宝玉对 Anthropic 官方博文《How Warp builds self-improving agents on Claude》的解读与延伸思考。原文讲的是终端工具 Warp 在内部用 AI 做 Code Review 时遇到的困境：Agent 不了解项目、不了解团队规范、记不住历史教训——本质上不是能力问题，而是没有记忆。

Warp 尝试过手动改系统提示词、完善 AGENTS.md，但两条路都不行：前者依赖人主动维护、成本高；后者浪费了团队成员在 PR 里自然写下的高质量评论。最终方案是一个「双 Skill」架构：一个基础 Skill 负责执行代码审查，一个改进 Skill（improver skill）作为观察者 Agent 定期运行——它拉取人类工程师对 Agent 审查结果的评论，对比 Agent 的建议与人类的实际反应，然后对基础 Skill 提出最小化的修改，走正常的 PR 流程合并。因为 Skill 本质是纯文本文件，Agent 非常擅长更新它，而且每次更新都可 review、可回滚。

宝玉在解读之外贡献了自己的第一手经验：他写过一个反编译 JS 代码的自我进化 Skill，效果不错但 Skill 文件越滚越大；也试过写作领域的自我进化 Skill，结果一言难尽——因为写作没有统一评判标准，Agent 经常负优化，越写越糟。这个对比恰好点出了 Warp 方案的适用边界。

关键洞察

  • 反馈摩擦决定进化速度：整套方案的精髓不在「自我改进」这个概念，而在摩擦力极低——人只要在 PR 下自然写评论，收集、提炼、更新 Skill 全部由 Agent 自动完成。反馈太麻烦，就收不到反馈，也就无法改进。
  • Skill ≠ Memory：Skill 是程序性、稳定的「如何做 X」，跨运行存在、由人刻意修改；Memory 是推理时自动写入、永远在变的。Warp 把「该沉淀的知识」放进 Skill 而不是塞进 prompt，这正是它可 review、可版本化的前提。
  • 写原则，不写死规则：Skill 要像指导一个聪明人，而不是给计算机编程。「寻找重复代码」比罗列详尽的变量命名规则更有效；解释规则背后的理由，Agent 才能举一反三。
  • 保持 Skill 精简 + 渐进式披露：好的 Skill 文件引用资源文件和脚本，而不是把所有内容一次性塞进上下文——这也顺便治了宝玉遇到的「Skill 越滚越大」问题。
  • improver skill 高度可复用：去掉领域知识部分，「改进 Skill」这套观察者机制几乎可以平移到任何 Agent 上——代码审查的 improver 和 issue 分类的 improver 区别不大，做一次收益多次。
  • 防错误反馈的三道闸：给 Agent 足够上下文做合理性检查、限制谁的反馈有权影响更新（领域专家优先，不开放给所有人）、最终始终保留人在循环中审核。有客观标准的领域（测试是否通过）先建验证基准，没有标准的领域（代码风格）靠专家判断。

评价

优点：选题踩在当前 Agent 工程最热的「自我进化 / 反馈闭环」话题上；宝玉没有停留在翻译，而是用自己的两个实战案例（反编译 Skill 成功、写作 Skill 失败）给原文补上了适用边界——有明确验证标准的领域才能安全地自我进化，这一层是原文没有明说的；6 条最佳实践条条可执行，拿来就能对照改进自己的 Skill 写法。

不足：作为解读型文章，核心框架仍来自 Anthropic 官方博文，独立增量主要集中在开头的个人经验部分；对「反馈分布漂移」（团队规范变了，旧 Skill 更新是否会互相冲突）这类更深的问题没有展开。

适用场景：正在维护 Agent Skill / CLAUDE.md / AGENTS.md 的开发者；想给团队 Agent 建反馈闭环但苦于「人肉改 prompt 不可持续」的工程负责人；对 Skill 与 Memory 边界感到困惑的人。
