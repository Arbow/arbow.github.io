李乾坤：群聊——Claude Agent Teams 的机制拆解，与”要不要上多 Agent”的冷思考

说明：本文发布于 2026-07-01，2026-08-14 有更新（页面标注更新时间），此前未被本系列收录过，本次补收。文章以 Claude 的 Agent Teams 为剖析对象，讨论”群聊式”多 Agent 协作。

核心概要

这是 李乾坤 Agent 系列的一篇技术笔记，主题是”群聊”——即多个 Agent 围绕同一目标协作的形态。文章先立了一个很清醒的前提：不是所有 Agent 场景都需要群聊，引入群聊的代价是显著的——无论是用户使用习惯，还是背后的 Agent Infra（技术架构、上下文管理、权限治理、并发调度、成本归因），每一项复杂度都会迅速拉高。真正需要群聊的场景被归纳为四类：跨领域协作（注意力在空间上的分散）、长链路工作流（注意力在时间上的衰减，几小时到几天的研发流程里，Agent 对早期信息的注意力持续被稀释）、多智能体治理、沉淀组织级知识。

文章最有分量的部分是对流行方案的批判性分析。”多 Agent + 软件工程团队角色”（PM 写 PRD、Architect 画架构、DEV 实现、SM 管 Sprint）是不是研发的全能解？作者的判断是：它是全能解，但不是最优解。全能解在于它确实能覆盖软件工程完整生命周期；不是最优解在于角色化本身引入三项具体成本：角色切换的上下文损耗（每次切换都是一次完整的上下文重建）、文档交接的信息衰减（”理解→文档→理解”的每次转换都有信息损失，人类团队靠会议弥补，Agent 团队靠什么？）、以及过程正确不等于结果正确（流程无懈可击不能弥补单步质量的不足——每一步输出质量取决于模型能力和上下文质量，而不是流程设计）。

由此给出的工程结论相当克制：大多数项目，单 Agent + 结构化上下文就够了；只在确实需要不同视角的关键环节（需求分析、代码审查）按需引入角色化；并行用在执行层，不是决策层——代码审查 6 个 Checker 并行、批量测试并行的收益最直接，而方案设计、架构决策这类需要深度思考的环节，并行反而带来冲突。

后半篇是对 Claude Agent Teams 机制的细致拆解：它本质上是基于本地文件系统的轻量级多 Agent 编排机制。角色包括 Team Lead（理解目标、拆任务、汇总）和 Teammates（执行）；协作通过四个原语实现——Shared Task List（任务写入 ~/.claude/tasks/{team-name}/，状态机 open → in_progress → completed，含 blocked/failed/cancelled 异常态）、Mailbox（异步点对点消息，写入 ~/.claude/teams/{team}/inboxes/ 下各 Agent 的 inbox 文件，消息发现靠定期检查而非推送）、Local File System（持久化任务、消息与协作状态）、文件锁（.lock 文件，写前拿锁写后释放，避免多个 Agent 同时写坏文件）。作者点出关键洞察：任务发现和消息发现本质上都是轮询/刷新共享状态，整个机制的核心不是”多个 Agent 同时干活”，而是共享状态驱动的多 Agent 协作——Subagent 是临时叫来帮忙的工具人，Agent Team 是围绕共享状态推进任务的项目组。

关键洞察

  • “要不要群聊”先看成本结构：上下文管理、权限治理、并发调度、成本归因——这套清单可以直接当成评估”是否引入多 Agent 架构”的检查表，多数场景会在第二项就暴露出投入产出不匹配。
  • 角色化三项成本值得抄进架构评审：上下文重建损耗、文档交接信息衰减、流程完备掩盖单步质量不足。尤其”过程正确≠结果正确”一条，戳破了大量 Agentic 工作流产品的营销叙事——决定输出质量的是每一步的上下文质量，不是流程图好不好看。
  • “并行用在执行层，不是决策层”：一句话可执行的工程原则。执行性工作（多 Checker 审查、批量测试）并行收益直接；需要深度串行思考的决策环节强行并行只会制造冲突。
  • Claude Agent Teams 的协作原语全部落在本地文件系统：task list + mailbox + lock 文件 + 轮询发现，没有消息总线、没有中心化调度器。这个设计换取的是可观测（一切皆文件，可直接 ls/cat 排查）、可恢复（断了能从断点续跑）、实现极简，代价是实时性（轮询延迟）和规模上限（单机文件系统）。这是”简单机制覆盖 80% 场景”的典型工程取舍。
  • 任务边界清晰是相对独立执行的前提：Team Lead 拆任务时最要紧的是保证每个任务边界清晰，这是任务能并行、能独立认领的先决条件——对任何做多 Agent 编排的人都适用。

评价

优点：机制拆解做到了目录结构和状态机级别——task 文件长什么样、inbox 消息的 JSON 字段、.lock 的加锁时机、Teammate 认领任务的完整流程（启动→读任务列表→发现 open 任务→判断适配→认领→置 in_progress），读者可以照着复现或验证，这在中文 Agent 技术文章里少见。判断部分不回避立场，”全能解但不是最优解”的论证链条完整，三个成本分析每条都给出了具体机制而不是泛泛而谈。写作风格直接，敢于对着行业热点泼冷水。

不足：结构未完成——开头的”简介”和结尾的”对 Agent Infra 提出了哪些新的挑战？”两节实际是空的（后者只是个占位标题，2026-08-14 的更新主要就是加入了这个占位），最值得展开的 Infra 挑战部分反而缺席，读完有意犹未尽之感。全文是笔记体，缺少与其它多 Agent 方案（如消息驱动的框架、中心化 orchestrator 路线）的横向对比，判断部分也没有实测数据支撑。对 Claude Agent Teams 的描述止于机制层，未讨论轮询频率、锁竞争、任务依赖死锁等工程细节的坑。

适用场景：正在评估”要不要把系统升级成 multi-agent 架构”的工程师和架构师（前半篇的批判性分析对决策直接有用）；想理解 Claude Agent Teams 内部机制、打算基于文件系统自建轻量多 Agent 协作的从业者（后半篇的拆解是难得的一手材料）。已经深度使用过多 Agent 框架、寻找深度对比的读者会觉得不够。

推荐指数

⭐⭐⭐ (3/5) — 机制拆解扎实、观点清醒的多 Agent 技术笔记，但结构未完成

理由：机制部分的拆解粒度和”全能解≠最优解”的批判性判断有真实价值，对正在做多 Agent 技术选型的读者是值得花十几分钟的参考；但文章本身未完成（两节空置，核心的 Infra 挑战只有标题没有内容），笔记体行文和缺失的横向对比限制了它的完整性，作为”必读”还不够格。定位为”有明确收获的参考读物”恰如其分。
